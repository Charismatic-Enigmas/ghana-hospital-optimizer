# Red-Black Tree: Rotation/Recolouring Evidence

`RedBlackTree` (`src/main/java/com/ghdsa/structures/RedBlackTree.java`) is a
left-leaning red-black tree (Sedgewick's formulation) — the brief explicitly
allows "a clear simplified balanced-tree implementation" as an alternative to
a classic RB-tree, and this is that: fewer rotation cases than a textbook
RB-tree, same balance guarantee (height <= 2 log2(n+1)).

The diagrams below were generated by simulating the exact same insert logic
as the Java implementation (not drawn by hand), then cross-checked against
`lastInsertRotationLog` from a live run of menu option 12 against real
request ids — the rotation sequence matches exactly:

```
insert(1) -> no rebalancing
insert(2) -> [rotateLeft@2]
insert(3) -> [flipColors@2]
insert(4) -> [rotateLeft@4]
insert(5) -> [flipColors@4, rotateLeft@4]
insert(6) -> [rotateLeft@6]
insert(7) -> [flipColors@6, flipColors@4]
insert(8) -> [rotateLeft@8]
```

`R`/`B` below mean the colour of the link from a node's parent (red = part of
a temporary 3-node, black = a normal 2-node link); the root is always forced
black after every insert.

## Case 1: single left rotation (insert 2)

A red right-link is illegal in a left-leaning RB-tree (`isRed(h.right) &&
!isRed(h.left)`), so it gets rotated left.

```
before insert(2):        after insert(2), rotateLeft@2:
  1(B)                       2(B)
                            /
                          1(R)
```

## Case 2: rotation + colour flip together (insert 5)

Inserting 5 first creates a red right-link at 4 (rotateLeft@4), which then
leaves node 4 with two red children -- `flipColors` pushes the "redness" up
to 4 itself and turns both children black:

```
before insert(5):              after insert(5):
      4(B)                            4(B)
     /                                 \
   2(R)                                5(B)
   / \                          [4 becomes red temporarily,
 1(B) 3(B)                       then flipColors makes it
                                  black again and 2 red]
```

Actual resulting shape (from the simulator, matches the live rotation log
`[flipColors@4, rotateLeft@4]`):

```
    5(B)
4(B)
    3(B)
2(R)
    1(B)
```

## Case 3: colour flip propagates upward (insert 7)

Inserting 7 causes `flipColors@6` (6 gets two red children from the earlier
rotation, so they flip to black and 6 turns red) — that new red-ness at 6
then makes node 4 also have two red children, so it flips too
(`flipColors@4`). No further rotation is needed because after the flip at 4,
no left-leaning-invariant rule is violated anywhere above it.

```
before insert(7):                    after insert(7):
        6(B)                                 6(B)
       /                                    /
     5(R)                                 5(B)
    /                                          [7 attaches under 6,
  4(B)                                          flipColors@6 fires,
 /    \                                         then flipColors@4
2(B)   [3(B) under 2]                           fires too]
```

## Height discussion

After 8 sequential ascending inserts (1..8, the worst case for an
*unbalanced* BST — see `BinarySearchTree` demo, menu option 11, which
degenerates to height 7 for the same input), this red-black tree's height
stays at **3** (`height()` reported by the live run). For n=8,
`2*log2(9) ~ 6.3`, comfortably above the observed height of 3 — the
self-balancing guarantee holds.

The efficiency lab (menu option 20, `bst_vs_balanced` experiment, graphed in
`docs/graphs/bst_vs_balanced_height.svg`) confirms this at larger scale on
the exact same sorted-worst-case input: plain BST height grows ~linearly
with n (observed: height 99 at n=100, height 9951 at n=10000 — i.e. height
~= n-1, a degenerate linked list), while red-black tree height stays
logarithmic (observed: height 6 at n=100, height 13 at n=10000 --
log2(10000) ~= 13.3, matching almost exactly).
